# ЧАСТЬ 2: ТЕКСТ ДОКЛАДА

**[Слайд 1 — Титульный]**

Добрый день! Меня зовут Лисицин Михаил, наша команда представляет проект «AI-помощник для аналитика в блоке HR». Заказчик — Сбербанк России, филиал Уральский банк.

**[Слайд 2 — Проблема]**

Каждый день сотрудники HR-блока Сбера работают с огромным потоком информации: новости рынка труда, изменения в законодательстве, тренды найма и сокращений, публикации на английском языке. HR-аналитик тратит до двух-трёх часов в день просто на мониторинг источников. При этом критически важные изменения — например, массовые сокращения в IT или новые регуляторные требования — могут быть пропущены, потому что ручной мониторинг запаздывает и не даёт целостной картины.

**[Слайд 3 — Целевая аудитория]**

Мы выделили три ключевых портрета пользователей. Первый — HR-аналитик, которому нужен мониторинг рынка и трендов. Второй — HR-партнёр, который следит за корпоративной культурой и выгоранием сотрудников. Третий — HR-руководитель, которому нужна стратегическая сводка для принятия решений. Для каждой роли агент предоставляет персонализированную информацию с разным фокусом и уровнем детализации.

**[Слайд 4 — Аналоги]**

Мы проанализировали существующие решения. ChatGPT и Perplexity могут анализировать тексты, но они реактивны — ждут запроса пользователя, не имеют памяти между сессиями и не умеют применять HR-специфичные правила. Аналитика hh.ru даёт статистику по вакансиям, но не мониторит новостной фон. Наше решение — это именно агент: он сам собирает данные, сам анализирует и сам генерирует рекомендации.

**[Слайд 5 — УТП]**

Наше ключевое отличие — формула AI-агента: состояние плюс правила плюс автономные действия. Первое — проактивность: агент сам находит важное и предупреждает, не ждёт запроса. Второе — персонализация без промптов: пользователь настраивает роль, темы и чувствительность через интерфейс, а не через текстовые команды. Третье — встроенная HR-доменная логика: словари терминов, риск-скоринг, детекция аномалий по семи HR-категориям.

**[Слайд 6 — Архитектура]**

Архитектура агента состоит из трёх компонентов. State — персистентное состояние, которое хранит историю наблюдений и тренды между циклами работы. Rules — HR-правила: расчёт риск-скоров по ключевым словам, пороги для уведомлений, детекция аномалий. И Actions — автономный цикл работы: агент собирает новости из RSS-лент, переводит через GigaChat, классифицирует, считает риски и генерирует инсайты.

**[Слайд 7 — Стек]**

В качестве основного языка мы используем Python. Для работы с LLM — GigaChat API от Сбера, что соответствует требованиям заказчика и хорошо работает с русскоязычной HR-терминологией. Для дашборда — Streamlit, для визуализации — Plotly. Парсинг RSS через feedparser, определение языка через langdetect.

**[Слайд 8 — Использование ИИ]**

GigaChat интегрирован в четырёх точках. Первая — перевод англоязычных новостей с сохранением HR-терминологии. Вторая — классификация текста по семи категориям: найм, сокращения, зарплаты, навыки, выгорание, культура, разнообразие. Третья — генерация проактивных инсайтов: это структурированная рекомендация с полями «что изменилось», «почему важно» и «что делать». Четвёртая — анализ трендов: сравнение текущих данных с историческими. При недоступности API каждый модуль имеет fallback-ответы, чтобы дашборд не падал.

Нажимаю «Запустить цикл анализа». Агент сейчас собирает новости из семи RSS-источников, переводит англоязычные через GigaChat, классифицирует каждую по HR-теме и считает риск-скор.

Каждый инсайт содержит: что произошло, почему это важно для HR и конкретную рекомендацию. Цвет карточки показывает уровень риска.

## Павленко Степан (архитектура, код)

> Архитектура построена по паттерну AI-агента: три компонента — State, Rules, Actions. State хранит состояние между циклами в JSON-файле: историю наблюдений, тренды, обработанные URL. Rules содержит HR-специфичные правила — словари ключевых слов для семи категорий и пороги рисков. Actions — это автономный цикл, где агент последовательно собирает данные, переводит, классифицирует, считает риски и генерирует инсайты. Весь LLM-функционал идёт через GigaChat с fallback-ответами при недоступности API.

## Коновалов Степан (тестирование)

GigaChat интеграцию — на корректность JSON-ответов и работу fallback при недоступности. Сквозной сценарий — от сбора данных до генерации инсайтов. Также проверяли граничные случаи: пустые RSS-ленты, тексты без даты, некорректные ответы от GigaChat.

## Беспамятных Евгений (данные, валидация)

Составили словари ключевых слов для риск-скоринга — негативные термины вроде «сокращения» и «выгорание», и позитивные — «найм», «обучение». Провели валидацию: прогнали через агент двадцать реальных новостей и проверили корректность классификации и адекватность инсайтов.
