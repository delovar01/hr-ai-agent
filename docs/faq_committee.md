## 1. Почему это «агент», а не чат-бот?

Бот ждёт промпта от пользователя. Наш агент:
- **Сам мониторит** RSS (26 источников, 14 активных)
- **Хранит state** между запусками: processed URLs, trends, insights
- **Применяет правила**: risk score, anomaly detection, alerts
- **Генерирует инсайты** без вопроса пользователя — формат «что произошло →
  почему важно → что делать»

RAG-чат «Спроси у HR-агента» — **дополнительный** интерфейс поверх
проактивного агента, не его замена.

## 2. Чем вы лучше ChatGPT/Perplexity?

| | ChatGPT | Perplexity | HR AI Agent |
|--|---------|------------|-------------|
| Инициатива | по запросу | по запросу | проактивно |
| HR-классификация | через промпт | через промпт | 7 фиксированных тем |
| Память | нет | нет | persistent state |
| Источники | весь интернет | весь интернет | курируемый пул (контроль качества) |
| Метрика качества | нет | нет | **Cohen's κ = 0.867** |

**Ключевое:** мы не универсальный поисковик — мы специализированный HR-радар.
Поэтому можем гарантировать **измеримое качество** на HR-задачах.

## 3. Зачем 7 тем, не 30? Не упрощение ли это?

7 тем — это **базовый HR-таксон** международного стандарта SHRM:
`hiring`, `layoffs`, `salaries`, `skills`, `burnout`, `culture`, `diversity`.
Для MVP этого достаточно — уже на 7 темах Cohen's κ = 0.867. Можем
показать измеримое качество на ограниченном пространстве, чем «всё подряд» с
непонятным качеством. В планах — расширение до 15 тем с пересчётом kappa.

## 4. Как вы масштабируете на 1000 источников?

В коде уже есть **`source_manager`** — модуль авторегуляции пула:
1. Каждый источник логирует события (`fetched`, `accepted`, `duplicate`).
2. `source_analytics` считает per-source метрики: `items_fetched`,
   `duplicate_rate`, `avg_risk_score`, `topic_coverage`, `unique_contribution`.
3. `source_manager` ранжирует источники и рекомендует деактивацию шумных и
   активацию ценных кандидатов.

То есть **не «добавим 1000 RSS и зальёт шумом»**, а контролируемый рост:
кандидаты проходят A/B-тестирование, дискриминируются по quality_score.

## 5. Почему JSON, а не SQL?

Для MVP — оптимально по time-to-value: zero-config, читается без БД,
видно в git, легко тестировать.

**Для production** заложили миграцию: PostgreSQL для observations/insights,
Redis для счётчиков, Celery для фонового запуска. Это план следующего
этапа после защиты. JSON ограничен ≈10к записей, мы это знаем.

---

## 6. Что с приватностью? Сбер не разрешит обрабатывать персональные HR-данные

В MVP **не используются** внутренние HR-данные Сбера. Только публичные
открытые источники (RSS-ленты, отраслевые медиа). API-ключ GigaChat — через `.env`.

При интеграции в Сбер — нужна авторизация по корпоративному SSO, разграничение
ролей (analyst / partner / manager уже заложены), хостинг внутри периметра
банка. Архитектура это поддерживает: state и LLM — изолированные модули.

## 7. Как обоснован риск-скор? Это же чёрный ящик

Нет, риск-скор **rule-based и прозрачный**:
- Ключевые слова с весами в `src/agent/rules.py`
- 4 уровня (`low/medium/high/critical`) с фиксированными порогами
- Пороги откалиброваны и описаны в `docs/METHODOLOGY.md`
- Аномалия = отклонение >30% от 30-дневного среднего

Это **намеренно** не ML — нам нужна интерпретируемость для HR-аналитика
(почему именно эта новость подсветилась). ML-уровень — план для следующей
итерации, поверх rule-based базы.

## 10. Что делаете после защиты? План развития?

Краткосрочно (1–2 недели):
- Расширение каталога до 50 источников (тестируем кандидатов через
  source_manager)
- Авто-запуск цикла по cron / GitHub Actions schedule
- Эмбеддинги для смысловой дедупликации (сейчас SimHash на тексте)

Среднесрочно (1–2 месяца):
- Миграция state на PostgreSQL
- A/B-тесты промптов GigaChat → рост kappa с 0.87 до 0.92+
- Интеграция с Telegram-каналами (через MTProto)

Долгосрочно (3+ месяца):
- Внутри-сберовский пилот на закрытых данных HR-управления
- Расширение до 15 HR-тем с пересчётом kappa

## 12. Дополнительные вопросы (если успеете)

**В.: Сколько стоит развернуть?**
О.: GigaChat API — бесплатный лимит покрывает MVP. Streamlit Cloud — бесплатный
тариф. Для пилота внутри Сбера — нужна виртуалка ≈$50/мес + платный GigaChat.

**В.: Время реакции агента?**
О.: ~30 секунд на цикл (26 источников × ~10 элементов + GigaChat-классификация).
В режиме авто-обновления — раз в 30 секунд по умолчанию.

**В.: Что если GigaChat недоступен?**
О.: Есть fallback на правила без LLM — классификация по ключевым словам.
Качество ниже, но агент не падает.

**В.: Почему именно GigaChat, а не OpenAI?**
О.: Заказчик — Сбер. Требование — российский LLM в периметре. GigaChat
обеспечивает суверенность данных и комплаенс ФЗ-152.
